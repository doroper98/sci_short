## 질문

바로 옆자리 친구에게 보낸 카톡은, 곧장 가지 않고 어디를 거쳐 갈까요?
(답: 메시지는 친구의 전화로 곧장 가지 않는다. 글자가 숫자(유니코드)가 되고, 0과 1의 신호가 되어 잠긴 채 패킷에 담기는데, 그 패킷의 받는 곳 주소는 친구의 전화가 아니라 메신저의 서버다. 패킷은 전파로 기지국까지, 거기서 광케이블 속 빛으로 데이터센터의 서버까지 간다. 서버가 받는 사람을 찾아 그 전화로 건넨다 — 앱이 연결돼 있으면 곧바로, 쉬고 있으면 운영체제의 알림 통로로 깨워서, 꺼져 있으면 맡아 두었다가. 친구가 읽으면 '읽었다'는 신호가 같은 길로 돌아와 숫자 1이 사라진다. 2022년 데이터센터 화재로 메시지가 멈춘 일이 '서버를 거쳐 간다'는 증거다.)

## 본질(제1원리)

"메시지는 친구의 전화로 곧장 가지 않고, 숫자가 되어 서버를 거쳐 갑니다." (s08 = s25)

- 상위 원리: **축적 전달(store-and-forward)과 패킷** — 통신망은 데이터를 작은 묶음(패킷)으로 나눠 주소를 붙여 나르고, 메신저는 그 위에서 '가운데의 컴퓨터가 받아 두었다가 건네는' 방식(클라이언트–서버)으로 일한다. 전화끼리는 서로의 위치(주소)를 모르고, 상대가 꺼져 있을 수도 있으므로 가운데가 필요하다(설명 모형).
- 묶음 8 제안의 명제("숫자로 바뀌고 잠긴 채 서버를 거쳐 갑니다")에서 '잠긴 채'를 뺐다 — 일반 채팅의 암호화 방식을 카카오가 공개한 자료로 확인하지 못했고, 한 문장 한 개념을 지키려고. 암호화는 s11 에서 메신저의 일반 원리로만 말한다.

## 메커니즘 단계

1. **글자 → 숫자 → 0과 1**(encode, s09~s10): 유니코드는 글자마다 번호를 정한 국제 약속. 한글 완성형 11,172자는 U+AC00(= 44032)부터 차례로 놓이고 '가'가 그 첫 글자(출처 7). 흔히 쓰는 UTF-8 방식에서 U+0800~U+FFFF 의 글자는 3바이트(= 24비트)(출처 8) → '가' = EA B0 80 = 11101010 10110000 10000000(직접 계산). 대본은 "흔히 쓰는 방식으로는"(카카오가 어느 방식을 쓰는지는 확인하지 않음).
2. **잠금과 패킷**(encode, s11~s12): 요즘 메신저는 보내는 길(전화 ↔ 서버)에서 메시지를 암호로 잠근다(일반 원리, 출처 9 의 설명). 카카오톡의 '비밀채팅'은 열쇠를 서버가 아닌 두 사람의 전화에만 두는 종단간 암호화(2014년 12월 발표, 출처 9) — 대본에는 넣지 않고 brief 에만(음절). 패킷의 받는 곳 주소는 서버(클라이언트–서버 메신저의 일반 구조, 설명 모형).
3. **전파 → 광케이블**(route, s13~s15): 전화는 전파로 가까운 기지국(또는 와이파이 공유기)까지. 기지국부터는 대개 광케이블(일부는 마이크로파 — "대개"). 유리(굴절률 약 1.47) 속 빛은 약 20만 km/s, 1 km 에 약 5 µs(출처 10). 전파 구간 왕복 지연은 4G 에서 약 40 ms(출처 11, 2019 국내 측정). 그래서 서울 안의 두 사람이면 전체가 보통 1초에 한참 못 미친다(s02 "보통 1초도 안 돼" — 어림 계산: 전파 두 구간 약 20 ms × 2 + 광케이블 수십 km 에 1 ms 미만 + 서버 처리; 전화가 잠들어 있으면 깨우는 데 더 걸릴 수 있어 "보통").
4. **서버**(server, s16~s17): 데이터센터는 서버 수만 대가 늘어선 건물 — 카카오가 2023년 9월 준공한 안산 데이터센터는 최대 12만 대(출처 12), 2022년 화재 때 판교에서 꺼진 카카오 서버는 약 3만 2천 대(출처 3). 받는 사람을 찾고 연결 상태를 본다(일반 원리).
5. **건네기 — 조건 하나: 친구 전화의 상태**(deliver, s18~s20): ① 앱이 열려 있으면 앱이 서버와 열어 둔 통로로 바로 ② 쉬고 있으면 휴대전화 운영체제(애플·구글)가 하나로 열어 둔 알림 통로로 서버가 알림을 보내 전화를 깨움 — 앱마다 통로를 열면 전지가 닳기 때문(출처 13) ③ 꺼져 있으면 서버가 맡아 두었다가 다시 연결될 때(축적 전달, 일반 원리).
6. **읽음**(read, s21~s22): 친구가 대화방을 열면 친구 전화가 '읽었다'는 짧은 신호를 서버로, 서버가 내 전화로 → 메시지 옆의 숫자 1(아직 읽지 않은 사람 수)이 사라짐. 숫자 1의 뜻은 사용자가 보는 화면의 동작(출처 14 — 공식 설명은 찾지 못함, 제3자 설명). 신호가 서버를 거쳐 온다는 것은 일반 원리(설명 모형).

| origin (약 20~45초) | (s04) 전신 손잡이가 눌림 → 짧고 긴 전류 펄스가 전선을 따라 다른 도시로 → 받는 쪽 종이띠에 점·줄이 찍힘 → (s05) 두 도시 사이에 중계국: 펄스가 들어와 종이띠에 다 쌓임 → 그다음에야 다음 줄로 나감 → (s06) 중계국 자리가 '서버' 상자로 바뀌고 양 끝이 휴대전화로 | 가운데 중계국이 없음/있음 하나. 곧장 간 펄스 길을 잔상으로 | "1844", 종이띠의 점·줄, 중계국에 쌓인 전보 수 | 펄스마다 낮은 삐(짧게·길게, 400 Hz), 종이띠에 찍힐 때 틱, 중계국에서 다시 나갈 때 휙 |
| essence (약 45~58초) | 내 전화 ─ 친구 전화 사이의 곧은 점선(곧장 가는 길, 흐리게) → 실제 길: 내 전화 → 서버 → 친구 전화로 신호가 감 → (s08) 명제 | 길 하나(곧장 / 서버를 거쳐). 곧은 점선은 잔상으로 남음 | 길 위의 고리 이름 | 신호가 서버에 닿을 때 틱, 친구 전화에 닿을 때 딩 |
| encode (약 58~85초) | 말풍선의 '가' → 번호 44032 가 뜸 → 번호가 0과 1 스물네 칸으로 펼쳐짐(8칸 × 3) → (s11) 칸들이 섞이며 잠김(자물쇠 모양 대신 칸의 무늬가 바뀜) → 봉투 모양 묶음(패킷)에 담김 → (s12) 묶음에 주소 꼬리표 '서버'가 붙음(친구 전화 쪽 화살표는 잔상) | 없음. 잠기기 전 0과 1 무늬를 잔상으로 | 큰 숫자 44032, 비트 수(24), 패킷 주소 | 숫자로 바뀔 때 낮은 톡, 비트가 펼쳐질 때 24번의 아주 짧은 틱, 잠길 때 쉭, 주소가 붙을 때 딸깍 |
| route (약 85~105초) | 패킷 → 전화 안테나에서 전파 고리가 퍼짐 → 기지국 안테나가 받음 → 광케이블 속 빛의 깜빡임으로 바뀜 → 데이터센터 쪽으로 달림 → (s15) 거리 자와 시간 계기가 같은 시계로 | 매체 하나(공기 속 전파 / 유리 속 빛). 전파 구간의 시간을 잔상으로 | 지난 시간(ms) 계기, 광케이블 옆 거리 자(km)와 빛의 위치 | 전파: 낮은 웅(220 Hz), 기지국이 받을 때 틱, 광케이블: 빠른 틱 줄(km 눈금마다) |
| server (약 105~118초) | 데이터센터 단면 → 서버 줄 사이로 패킷이 들어감 → 한 서버가 받음 → 받는 사람 목록에서 친구를 찾음 → '연결됨?' 표시가 켜짐 | 없음 | 서버 수 "수만 대", 연결 상태 표시 | 서버가 받을 때 낮은 딸깍, 찾을 때 짧은 틱 줄 |
| deliver (약 118~140초) | 같은 서버 → 친구 전화로 세 번: ① 연결됨: 열린 통로로 곧장 → 화면에 메시지 ② 쉬는 중: 알림 서버(운영체제)로 → 알림이 전화를 깨움 → 앱이 메시지를 받아 감 ③ 꺼짐: 서버의 보관함에 쌓임 → 전화가 켜짐 → 그때 건넴 | **친구 전화의 상태 하나**(연결됨 / 쉬는 중 / 꺼짐). 앞 경우의 길과 도착 시각을 잔상으로 | 도착까지의 시간 막대 세 개(어림, '쉬는 중'은 깨우는 시간 포함, '꺼짐'은 켜질 때까지) | 도착 딩, 깨울 때 두 번 톡, 보관함에 쌓일 때 둔한 톡 |
| read (약 140~155초) | 친구가 대화방을 엶 → 친구 전화에서 한색 '읽음' 신호가 나감 → 서버 → 내 전화 → 내 화면의 숫자 1이 사라짐 | 없음. 갈 때(난색)와 올 때(한색) 길을 함께 | 숫자 1(사라지는 순간), 지난 시간 | 읽음 신호: 높이가 다른 틱(330 Hz), 1이 사라질 때 짧은 톡 |
| myth (약 155~170초) | 데이터센터의 서버 줄이 꺼짐(어두워짐) → 두 전화 사이의 신호가 서버 앞에서 멈춤 → 멈춘 시간 계기 "약 10시간" → (s24) 곧장 잇는 점선(가정)이 나타나지만 실제 길은 서버를 지남 | 서버 켜짐/꺼짐 하나. 켜졌을 때의 신호 길을 잔상으로 | 멈춘 시간(시간), "2022.10" | 꺼질 때 낮게 내려가는 음, 멈춘 신호 앞에서 무음 |
| close (약 170~178초) | 처음의 두 전화 → 신호가 서버를 거쳐 친구 전화로 → 숫자 1이 사라짐 → 결론 글 → 끝 한 줄 | 첫 장면과 같은 시점 | 지난 시간 | 잦아드는 낮은 음 |

- 무대: 하나의 '길' — 아래에 책상 위의 두 전화(내 것 왼쪽, 친구 것 오른쪽), 그 위에 기지국 안테나 탑, 맨 위에 데이터센터 건물. 길은 아래 → 위 → 아래의 ∩ 모양이고, 왼쪽 오름길은 내가 보낸 것(난색), 오른쪽 내림길로 친구에게. 세계 안의 눈금: 길 옆 거리 자(가장 위가 '수십 km — 어림', 크기 과장 표식)와 지난 시간 계기(ms). origin 만 무대 밖(전신)이고 끝에 이 무대로 이어진다. encode 는 내 전화 화면을 키운 렌즈(테두리·지시선으로 이음).
- 채워진 무광 덩어리로 그릴 주인공: 휴대전화 두 대(둥근 모서리의 짙은 몸체, 면과 명암, 화면은 어두운 판 — 메신저 화면은 이름 없는 말풍선 하나), 기지국 탑, 데이터센터 건물과 서버 랙, 전신 손잡이·중계국.
- 빛나는 것과 그 뜻 — `lit()` 안에서 그린다: ① 메시지 신호 점(패킷이 길 위를 가는 것 — 신호, 난색) ② 전파 고리(전파 에너지) ③ 광케이블 속 빛의 깜빡임(빛) ④ '읽음'·알림 신호 점(신호, 한색) ⑤ 전신 전류 펄스(신호) ⑥ 켜진 서버의 작은 상태 불빛(신호, 아주 작게). 전화 화면이 켜지는 것은 **화면의 빛**이지만 면적이 넓어 `lit()` 에 넣지 않는다(흰 판이 번쩍이면 안 됨 — 화면은 SDR 밝기 그대로). 자막·계기·이름표·머리글·바탕도 넣지 않는다. 글을 빛 위에 얹는 곳(포스터 띠, 머리글, 계기판, 끝 글)은 빛 지도를 지운다(`unlitRect`, 포스터가 머리글로 줄어드는 동안 포함 — 50번 교훈).
- 난색이 맡는 역할: **내가 보낸 메시지**(신호 점, 오름길, 주제어). 한색이 맡는 역할: **돌아오는 것**(읽음 신호, 알림, 내림길에서 친구 쪽으로 건너가는 것은 그대로 난색 — 메시지는 끝까지 같은 색, 한색은 '읽음'과 '알림'만). 
- 시간 배율: hook "실제 1초 안 · 느리게", route "실제 1000분의 몇 초 · 아주 느리게", deliver '꺼짐'은 "켜질 때까지 건너뜀". 장면 키커에 한 번씩. 시간 계기의 ms 는 어림값이라고 이름표에 "어림".
- 글자 셋: 머리글 / 큰 숫자 하나(4,700만, 1844, 44032, 20만 km/s, 10시간) / 계기 눈금.
- 먼저 렌더할 핵심 장면 약 10초: hook 첫 3초(첫 순간 수치), deliver 의 세 경우 비교.

## 현상·사례

- 친구 전화의 상태에 따라 건네는 길이 다르다(deliver) — 조건 하나 비교.
- 2022년 10월 15일 오후 3시 30분쯤 판교 SK C&C 데이터센터 전기실 화재로 카카오톡이 멈췄고, 모바일 텍스트 메시지 수발신은 16일 오전 1시 31분쯤 일부 복구됐다(약 10시간, 출처 3). 카카오톡 출시 뒤 가장 긴 장애였다(출처 3). → s23 "열 시간쯤 오가지 못했습니다".

## 오해 바로잡기

- "옆자리 친구에게는 전화끼리 곧장 간다" → 아니다. 받는 곳 주소부터 서버이고(s12), 서버가 멈추자 메시지도 멈췄다(s23~s24).

"메시지는 친구의 전화로 곧장 가지 않고, 숫자가 되어 서버를 거쳐 갑니다." (s25 = s08)

## 공간·카메라

- '길' 무대 하나. 카메라는 hook 의 결과 먼저(물러남 → 되감기), encode 의 렌즈(내 전화 화면으로 들어감), myth 끝의 물러남에서만 움직이고 비교(deliver 세 경우) 중에는 서 있다.
- 계기는 오른쪽 위·가운데(1240 위, x 940 안). 자막 baseline 1380.

## 소리 이벤트

모두 합성한 설명용 소리(녹음 아님), `sound.json` 사건 98개, 기본음·잡음 대역 모두 700 Hz 아래(가장 높은 것 600 Hz — 0과 1 칸의 틱). 화면과 같은 시각표(`events.json` 대조 통과). 신호 점의 위치를 이 사건 시각 사이에서 보간하므로 그림과 소리가 같은 표를 쓴다.

| 사건 | 소리 | 화면에서 같은 순간 |
|---|---|---|
| `*_send` | 520 Hz 틱(메시지) / 440 Hz(읽음) | 신호 점이 전화를 떠남 |
| `*_rf1`·`*_rf2` | 180↔520 Hz 휙(대역 잡음) | 전파 고리가 퍼짐 |
| `*_ant`·`*_ant2` | 330 Hz 틱 | 기지국 안테나를 지남 |
| `*_dc` | 196 Hz 짧은 음 | 데이터센터에 닿음(서버 불이 켜짐) |
| `*_out` | 262 Hz 틱 | 서버에서 나감 |
| `*_arr` | 392 Hz 딩(메시지) / 349 Hz(읽음 — 숫자 1이 사라짐) | 친구 화면에 뜸 / 1 사라짐 |
| `hk_rewind` | 600→160 Hz 휙 | 되감기 |
| `mo_*`·`ri_*`·`ro_*` | 400·330 Hz 음(점은 짧게, 줄은 길게) | 전신 전류 펄스, 중계국에 들어옴·나감 |
| `enc_*` | 247 Hz(번호) · 600 Hz 틱 ×24(0과 1 칸) · 대역 잡음(잠금) · 220 Hz(패킷) · 350 Hz 틱(주소) | 렌즈의 각 단계 |
| `rt_fiber` | 300 Hz 틱 ×5(10 km 눈금마다) | 광케이블 확대의 빛 |
| `sv_*` | 165 Hz · 500 Hz 틱 ×5 · 294 Hz | 서버가 받음 · 찾기 · 연결 확인 |
| `d1_*`·`d2_*`·`d3_*` | 위와 같은 짝 + 440 Hz 두 번(깨움) · 147 Hz(맡아 둠) · 196/294 Hz 부풂(켜짐) | 세 경우의 전달 |
| `my_off`·`my_stop` | 300→80 Hz 내림 · 150 Hz 틱 | 서버가 꺼짐 · 메시지가 서버 앞에서 멈춤 |

## 단순화 메모 (관측 / 설명 모형 / 비유)

- s01·s24 "옆자리 친구": 같은 방의 두 사람 — 둘 다 이동통신(또는 와이파이)으로 인터넷에 붙어 있는 경우. 블루투스 같은 근거리 직접 연결은 메신저가 쓰지 않는 길이라 말하지 않음.
- s02 "보통 1초도 안 돼": 어림 계산(위 메커니즘 3). 전화가 잠들어 있거나 전파가 약하면 더 걸린다("보통").
- s03 "4,700만 명 넘게": 와이즈앱·리테일 표본 집계 2026년 6월 4,797만·7월 4,744만(출처 1). 카카오 자체 발표(국내 MAU 약 4,963만, 2026년 2분기)는 셈법이 달라 쓰지 않음. 관측(집계).
- s04: 관측 사실(역사). 화면의 모스 부호 점·줄은 실제 메시지의 부호가 아니라 모양만(정성적).
- s05: 관측 사실(중계국이 받아 두었다가 다시 보냄). 사람이 받아 적어 다시 보내던 19세기 중계국과 20세기 테이프 중계를 함께 가리킴 — 화면 이름표는 '중계국'만, 시기는 "전보가 많아지자"로 뭉뚱그림.
- s07·s08·s12: 설명 모형(클라이언트–서버). 실제로는 서버가 여러 대이고 중간에 라우터·교환기가 많다 — 화면은 기지국 하나, 광케이블 한 줄, 데이터센터 하나로 줄였다.
- s09·s10: 관측(규격). "흔히 쓰는 방식" = UTF-8. 카카오톡이 내부에서 어떤 부호화를 쓰는지는 확인하지 않음.
- s11 "암호로 잠긴 뒤": 메신저의 일반 원리(전송 구간 암호화). 카카오 일반 채팅의 구체적 방식은 확인하지 못해 말하지 않음.
- s13 "전파": 이동통신(4G·5G). 와이파이면 공유기 — 화면 이름표에 "(와이파이면 공유기)".
- s14 "대개 광케이블": 기지국 뒤 연결은 대부분 광케이블, 일부 무선(마이크로파).
- s16 "수만 대": 카카오 데이터센터 수치(출처 3, 12)에 맞춘 어림.
- s19 "운영체제의 알림 통로": 애플 APNs·구글 FCM 의 일반 원리(출처 13). 카카오가 어느 알림 서비스를 쓰는지 대본은 말하지 않음.
- s20 "맡아 두었다가": 축적 전달의 일반 원리. 카카오의 서버 보관 기간은 확인하지 못해 말하지 않음(2014년 기사의 2~3일은 오래된 자료).
